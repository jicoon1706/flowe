### Root cause (from source; the trigger on your device is **[unverified]**)

On Android, the modal's JS root is not sized from the modal window. Its size comes from Fabric state,
and on the first frames that state is wrong:

- `node_modules/react-native/ReactCommon/react/renderer/components/modal/ModalHostViewState.h`: the
  default constructor seeds `screenSize` from `ModalHostViewScreenSize()`. On Android that calls
  `ReactModalHostView.getScreenDisplayMetricsWithoutInsets()` over JNI.
- `node_modules/react-native/ReactAndroid/.../views/modal/ReactModalHostView.kt:493-498` returns
  **screen height − `statusBarHeight`**. With edge-to-edge the dialog window covers the full screen, so
  this is too short. `statusBarHeight` is a static cached at `:134` / `:487-489` whenever *any* modal
  host view is created on the UI thread, and the JS-side commit reads it.
- `ModalHostViewComponentDescriptor.h` (`adopt`) gives the modal's shadow node exactly that size.
  RN's `Modal.js` container (`flex: 1`) fills that size and nothing more, and so does everything inside
  `SystemModal` and `Sheet`.
- The only correction is asynchronous. The dialog's root view gets its first native layout, then
  `onSizeChanged` (`:544-549`) calls `updateState` (`:553-563`), and that commits the real size back
  through Fabric. Until that round trip lands, the scrim and the panel stop 24 dp short of the bottom.
  On this emulator, 731.43 − 24 = 707.43, and 24 dp is the gesture-nav bar's height: the band you
  described. Cold start is when the UI thread is busiest, so it's when the round trip lands latest.
  Later opens are fast enough that you never see it.
- Upstream confirms the defect. RN PR #52835, "Correctly create the first modal state", merged
  2025-08-07, says the first frame of new-arch modals doesn't account for all vertical insets and that
  the cached status-bar height "could read 0". It removes the cache and sizes the first state from the
  activity's insets. Our RN 0.81.5 still has the old code.

**How to tell them apart on a device:** switch to 3-button navigation and reproduce. If the band is
**24 dp** (the status-bar height), it's the Fabric first-state case, which this fix covers. If it's
**48 dp** (the 3-button nav bar), the dialog window itself wasn't edge-to-edge, and only a native
change can fix that (see section 5).

### Fix (one place, every sheet and modal benefits)

`components/ui/SystemModal.tsx`: on Android, the nested `SafeAreaProvider` is pinned to the window,
`position:absolute, top 0, left 0, width/height = useWindowDimensions()`. It no longer depends on the
Modal host's state round trip. The scrim, the panel, and the provider's own inset measurement are full
height from the first frame. iOS is unchanged: it keeps the default `flex:1` fill, so presentation
styles still work. `Sheet.tsx` is unchanged.

- Window dimensions are the right size. In the log, `window` = `screen` = the dialog window,
  edge-to-edge. In split-screen on a tablet, `window` is the activity's bounds, which is what the
  dialog uses.
- If the modal root is briefly short, the pinned provider overflows it. RN views don't clip by default,
  and the dialog's native root is the full window, so the overflow is drawn.
- `testID="system-modal-root"` was added so the test can find the provider.
