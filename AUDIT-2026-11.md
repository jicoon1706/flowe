## How the two apps relate (why most findings are "both")

Most of desktop's data layer is a copy of mobile's: `money.ts`, `budget.ts`, `cashflow.ts`,
`calendarSpend.ts`, `tabungProgress.ts`, `addTransactionValidation.ts`, `utils/date.ts` and most
repositories are byte-identical (only import paths differ). `transactions.repository.ts` adds the
desktop table query; `services/recurring.ts` is a trimmed port. A bug in shared logic is therefore in
both apps, and each fix below is applied to both copies so they stay identical.

### Checked and found correct (no finding)

- Balance legs: `applyBalanceEffect` (client) and `recalculate_account_balances` (SQL) agree on every
  transaction type, including transfers, investments and tabung top-up/withdraw with a funding account.
- `localYMD` is used for every "today" in both apps; no `toISOString().slice(0, 10)` and no bare
  `new Date('YYYY-MM-DD')` left in app code. Month boundaries in `fetchByMonth` use local dates.
- Recurring due cutoff (`dueThroughYMD`, 05:00 local) is identical in both apps; monthly anchoring
  and short-month clamping are correct and specced.
- Money formatting (`roundCents`, `splitMoney`, `formatRM`, `parseAmount`) is identical and specced
  in both apps; tabung pay-out can't exceed the jar's balance in either app.
- Transfer validation refuses the same account on both ends in both apps.
- Cashflow info totals (cash, assets, liabilities, class) compute the same figures on mobile and desktop.
- Desktop pairing / PIN: the PIN is verified server-side only; the desktop never holds the hash.

## B10: opening amount for tabung (option a, approved 2026-11-18)

- **Migration `supabase/migrations/20261121_tabung_opening_amount.sql`:**
  1. adds `tabung_accounts.opening_amount numeric not null default 0`;
  2. backfills existing jars: `opening_amount = max(0, saved_amount − Σ transactions)`, so the next
     Recalculate leaves every jar where it is today. A jar whose starting amount was already wiped by an
     earlier Recalculate can't be recovered (nothing records it);
  3. replaces `recalculate_account_balances`: a jar is rebuilt as `opening_amount + Σ transactions`.
     Banks and wallets are unchanged.
- **Client (both apps):** `createTabungAccount` also writes `opening_amount` when a starting amount is
  given; `TabungAccount` type has the new field. Spec: `tests/tabungOpeningAmount.test.ts`.
- **Order matters:** apply the migration **before** shipping these builds. Until it's applied, creating a
  tabung *with* a starting amount fails (unknown column); empty jars are unaffected.
- **Unchanged:** the progress ring still counts top-ups only in "contributed" mode, so a starting amount
  doesn't count toward the goal there (it does in "balance" mode). Same as before this change.
- **Not yet done:** applying the migration to the live `flowe` project.
